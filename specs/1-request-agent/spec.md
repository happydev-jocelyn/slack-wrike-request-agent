# Spec: Slack 요청 → Wrike 등록 에이전트            (specs/1-request-agent/spec.md)

## 1. 의도 (무엇을·왜·누구를 위해)
- 무엇을: Slack 채널에서 받은 업무 요청을 Wrike 티켓(검토중)으로 등록하고, AI가 기존 티켓·일감과 비교한 의견을 남기며, 지정된 승인자가 확정하면 Wrike '전체 일감'에 일감을 만든다.
- 왜: 요청 창구는 Slack인데 일감 정본은 Wrike다. 지금은 사람이 옮겨 적고, 중복·유사 요청을 사람이 기억으로 걸러야 한다.
- 이걸로 사용자가 할 수 있게 되는 것:
  - 요청자: 채널의 버튼 하나로 요청을 등록하고 진행 상태를 Slack에서 본다.
  - 승인자: Slack에서 AI 의견을 보고 ✅/❌ 한 번으로 확정·반려한다.
  - 관리자: 서버를 건드리지 않고 Slack 홈 탭에서 Wrike 연결 정보를 바꾼다.

## 2. 인수조건 (AC)
가정: Wrike가 정본이다. 앱은 일감 데이터를 따로 저장하지 않는다(설정만 저장).

**요청 등록**
- [ ] AC1: Given 요청 채널에 '요청 등록' 버튼 메시지가 있고, When 사용자가 버튼을 누르면, Then 카테고리·일감 제목·일감 내용·담당자 입력 폼이 열린다. 채널 상단에 상시 노출된다(고정은 관리자가 수동으로 한다).
- [ ] AC2: Given 폼을 모두 채워 제출하면, Then Wrike에 티켓 1건이 상태 '검토중'으로 생성되고(제목·내용·카테고리·담당자·요청자·Slack 메시지 링크 포함), 채널에 Wrike 링크가 담긴 "새 요청 · 검토중" 메시지가 1건 게시된다.
- [ ] AC15: Given 앱이 설치돼 있으면, Then 버튼 말고도 `/request` 명령, 전역 단축키(⚡ 메뉴 "요청 등록"), 메시지 단축키(메시지 ⋯ 메뉴 "Wrike 요청으로 등록")로 같은 폼을 열 수 있다. 메시지 단축키로 열면 그 메시지 내용이 '일감 내용'에 미리 채워진다. 어느 입구로 등록해도 요청 메시지는 요청 채널에 게시된다.
- [ ] AC16: Given 요청 채널에 사람이 새 글(스레드 답글·봇 메시지·수정·삭제 제외)을 쓰면, Then 작성자에게만 보이는 "Wrike 요청으로 등록할까요? [등록]" 안내가 뜨고, [등록]을 누르면 그 글이 '일감 내용'에 채워진 폼이 열리며 안내는 사라진다. 다른 사람에게는 아무것도 보이지 않는다.
- [ ] AC3: Given Wrike 호출이 실패하면, Then 티켓도 채널 메시지도 만들어지지 않고 요청자에게만 실패 사유가 보인다.

**AI 의견**
- [ ] AC4: Given 티켓이 생성되면, Then 진행 중이거나 최근 90일 안에 생성된 티켓·일감과 비교한 의견(유사 건 링크 0~3개 + 한두 문장)이 해당 Slack 메시지 스레드와 Wrike 티켓 댓글 양쪽에 남는다.
- [ ] AC5: Given 유사 건이 없으면, Then "유사한 기존 일감 없음"이라고 남긴다. AI는 상태를 바꾸지 않는다(의견만).
- [ ] AC6: Given AI 호출이 실패하거나 AI가 꺼져 있으면, Then 등록·승인 흐름은 그대로 진행되고 스레드에 "AI 의견 생성 실패"만 남는다.

**승인·반려**
- [ ] AC7: Given 승인자가 '새 요청' 메시지에 ✅를 누르면, Then Wrike 티켓이 '확정'이 되고, '전체 일감' 폴더에 일감 1건이 생성되어 티켓과 서로 링크되며, 스레드에 일감 링크가 달린다.
- [ ] AC8: Given 승인자가 ❌를 누르면, Then 티켓이 '반려'가 되고 스레드와 Wrike 티켓 댓글에 반려자가 기록된다. 일감은 생성되지 않는다.
- [ ] AC9: Given 승인자가 아닌 사람이 ✅/❌를 누르면, Then 아무것도 바뀌지 않고 그 사람에게만 "권한 없음" 안내가 보인다.
- [ ] AC10: Given Wrike에서 티켓이 이미 확정·반려·삭제된 상태에서 ✅/❌를 누르면, Then 아무것도 바꾸지 않고 스레드에 현재 상태를 알린다(같은 ✅를 두 번 눌러도 일감은 1건).

**설정·운영**
- [ ] AC11: Given 관리자가 앱 홈 탭을 열면, Then Wrike 토큰·지역 호스트·프로젝트·요청 폴더(기본 "요청")·전체 일감 폴더(기본 "전체 일감")·티켓 유형(선택)·**요청 워크플로(기본 "요청 처리") 와 그 안의 상태 3개(검토중·확정·반려)**·요청 채널·승인자·카테고리·AI 켜기/끄기를 입력·저장할 수 있다. 프로젝트·폴더·티켓 유형·상태는 각각 **이름 또는 ID** 어느 쪽으로든 넣을 수 있다. 관리자가 아니면 설정 화면이 보이지 않는다.
- [ ] AC12: Given 설정을 저장하면, Then 앱이 입력값이 ID면 그대로 확인하고, 이름이면 Wrike에서 찾아 ID를 채운 뒤 결과(이름·ID)를 보여 준다. 요청 티켓은 기존 업무 워크플로와 분리된 **전용 요청 워크플로**를 쓴다. 그 워크플로가 없으면 "워크플로 만들기" 버튼으로 검토중·확정·반려 상태를 가진 새 워크플로를 만들고, 있는데 상태가 빠졌으면 그 전용 워크플로에만 상태를 추가한다. 기존 업무 워크플로는 읽기만 하고 바꾸지 않는다. 확정 시 '전체 일감'에 만드는 일감은 그 폴더의 기존 워크플로 기본 상태로 생성한다. 프로젝트나 폴더가 없으면 "만들기" 버튼을 보여 주고, 누르면 그 이름으로 생성한다. 이름이 여러 개 겹치면 후보를 골라야 저장된다. 저장된 토큰은 화면·로그에 다시 표시되지 않고 암호화되어 저장된다.
- [ ] AC13: Given 앱이 실행 중이면, Then 홈 탭에 "실행 중 · 마지막 확인 시각 · Wrike 연결 상태"가 보인다.
- [ ] AC14: Given 남편 PC에 Docker가 있으면, When `docker compose up -d`를 실행하면, Then 앱이 뜨고 PC 재부팅 후에도 자동으로 다시 실행된다. 설정은 컨테이너 재생성 후에도 유지된다.

## 3. 범위 & 비목표
- 포함: 위 AC1~AC16. 워크스페이스별 설정 분리(설정을 워크스페이스 단위로 저장).
- 하지 말 것(non-goals):
  - Slack 리스트 사용, 5일 자동 삭제(Wrike가 정본이므로 불필요)
  - Wrike 안에서 직접 상태를 바꾼 경우의 Slack 동기화(필요 시 후속)
  - AI의 자동 반려·자동 병합
  - Slack Marketplace 배포, ROSI(Deno) 배포, 호스팅 서비스 배포 버튼
  - Python 직접 실행 설치 스크립트(README에 수동 방법만)
  - 등록 버튼을 채널 맨 아래로 다시 올리는 기능(필요 시 후속), 멘션 자연어 등록

## 4. 제약
- 스택 / 런타임: Python, Bolt for Python(Socket Mode), Docker Compose. 남편 회사 PC에서 실행. 공인 IP·인바운드 포트 없음.
- 외부: Wrike API v4(지역 호스트 설정 가능), Claude API. 회사 Slack은 Enterprise.
- 따라야 할 기존 컨벤션: 데모(`request-demo/app.py`)의 흐름과 이름을 이어 간다. 코드 주석·커밋은 한국어.

## 5. 파일/모듈 계약
- 계층: 순수 로직(의견 프롬프트 구성·응답 파싱·권한/상태 판정) → 경계(Wrike·Claude·설정 저장소 클라이언트) → 배선(Bolt 핸들러·홈 탭 UI).
- 상세 파일 구성은 `/tasks` 단계에서 정한다.

## 6. 자기검증 방법
- 순수 로직: `python3 -m unittest discover -s tests -t .` green (추가 설치 없이 표준 라이브러리로 실행).
- 경계: Wrike·Claude 클라이언트는 응답 고정(fake) 계약 테스트. 실제 Wrike 호출은 남편 토큰으로 마일스톤 게이트에서 1회 확인.
- 배선: 테스트 Slack 샌드박스(test02)에서 실행해 AC1~AC13을 관찰. Wrike는 실제 계정이 없으면 가짜 서버로 대체하고, 그 사실을 보고한다.

## 7. 리스크
- [NEEDS CLARIFICATION: 남편 Wrike의 '티켓'이 사용자 정의 항목 유형인가, 일반 일감+요청 폴더인가] — 둘 다 설정으로 지원하되, 실제 확인 전엔 한쪽만 검증 가능.
- 가정: 이름으로 못 찾은 프로젝트·폴더는 관리자가 버튼을 눌렀을 때만 만든다(자동 생성 안 함). 전용 요청 워크플로와 그 상태도 관리자가 버튼을 눌렀을 때만 만든다. 워크플로 생성·수정에는 Wrike 워크플로 쓰기 권한(amReadWriteWorkflow, 계정 관리자급)이 필요하며, 권한이 없으면 실패 사유를 보여 주고 Wrike 관리자가 수동으로 만든 워크플로를 이름·ID로 지정하게 한다.
- 리스크: Wrike 공간(space) 설정이 허용된 워크플로만 쓰게 막아 두었거나, 티켓 유형(사용자 정의 항목 유형)에 워크플로가 고정돼 있으면 전용 워크플로를 쓸 수 없을 수 있다(미확인). 이 경우 공간에 워크플로를 허용하는 것은 Wrike 관리자가 한다.
- 회사 Enterprise Slack의 앱 설치 승인, 사내 프록시, Docker Desktop 라이선스, 외부 AI로 업무 데이터 전송에 대한 회사 정책.
- PC가 꺼지면 버튼·✅가 동작하지 않는다(요구상 수용).
- 보상 호출까지 실패하는 이중 장애는 자동 복구하지 않고 안내로 처리한다(수용): 등록 되돌리기 중 티켓 삭제가 실패하면 남은 티켓 링크를 요청자에게 안내, 확정 중 일감 생성 실패 뒤 검토중 되돌리기도 실패하면 스레드에 Wrike에서 직접 되돌리라고 안내, 확정 뒤 Wrike 댓글이 실패하면 티켓→일감 링크는 스레드에만 남는다.
- Wrike 실계정 없이 개발하므로 실제 API 응답 형태 차이는 게이트에서야 드러난다.
